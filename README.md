# JobsOperator

JobsOperator — экспериментальная платформа на .NET 10 для описания, запуска и наблюдения за потоковыми заданиями. Задание реализует контракт `IJob` и собирает один или несколько конвейеров вида:

```text
Source -> Process -> Sink
```

Проект поддерживает чтение данных из JSON Lines и Kafka, пользовательскую обработку, запись в Kafka или произвольный sink, состояние задания, согласованные контрольные точки и запуск сборок через веб-интерфейс.

## Состояние проекта

Репозиторий находится на стадии прототипа. Основной сценарий уже работает, но публичный API, формат контрольных точек и поведение среды выполнения могут изменяться без обратной совместимости.

Реализовано:

- типизированное описание конвейера `Source -> Process -> Sink`
- несколько независимых конвейеров в одном задании
- ограниченный внутренний канал на 128 записей для обратного давления
- источники JSON Lines и Kafka
- Kafka sink с `acks=all` и идемпотентным producer
- sink `Discard` для конвейеров без внешнего результата
- потокобезопасное состояние `IState<T>`
- периодические контрольные точки позиций источников и состояния задания
- режимы запуска `ResumeOrCreate`, `ResumeOnly` и `CreateNew`
- запуск, остановка и получение диагностического снимка через `JobsOrchestrator`
- REST API для загрузки DLL, чтения, запуска, остановки и удаления заданий
- отдельный gRPC Worker, внутри которого выполняются задания и хранится их оперативное состояние
- Blazor Server-панель, работающая с заданиями только через REST API
- отображение статуса, числа обработанных сообщений, последнего сообщения и содержимого зарегистрированных состояний
- Docker Compose-стенд из трёх Kafka-брокеров, Kafka UI и контейнерного раннера

## Требования

- .NET SDK 10.0
- Docker с поддержкой Docker Compose для Kafka-сценария
- PowerShell, Bash или совместимая командная оболочка

Проверить установленную версию SDK:


## Быстрый запуск

Восстановить зависимости и собрать решение:

```shell
dotnet restore JobsOperator.sln
dotnet build JobsOperator.sln
```

### Консольный пример

Запустить `SampleJob`:

```shell
dotnet run --project JobsOperator
```

Задание читает `JobsOperator/Test.json` в формате JSON Lines, сохраняет элементы во внутреннем состоянии и выводит их в консоль. После достижения конца файла источник продолжает ждать новые строки. Для завершения нажмите любую клавишу.

Пример входного файла:

```json
{"Name":"Nastya"}
{"Name":"Pasha"}
```

### Веб-интерфейс

Запустить Worker, REST API и панель в отдельных терминалах:

```shell
dotnet run --project JobsOperator.Worker --launch-profile http
dotnet run --project JobsOperator.Api --launch-profile http
dotnet watch --project JobsOperator.Web
```

Адрес HTTP-профиля по умолчанию:

```text
http://localhost:5088
```

Порядок работы:

1. Соберите проект с реализацией `IJob`
2. Откройте главную страницу панели
3. Выберите DLL задания и все необходимые DLL-зависимости
4. Нажмите `Добавить и запустить`
5. Используйте карточку задания для остановки, удаления или повторного запуска

Ограничения загрузки:

- принимаются только файлы `.dll`
- не более 20 файлов за одну загрузку
- общий размер не более 100 МБ
- реализация `IJob` должна быть конкретным классом с публичным конструктором без параметров
- запускаются все найденные в загруженных сборках реализации `IJob`
- контракт `Jobs.dll` предоставляет сервер; загружать собственную копию этой сборки не требуется

Загруженные файлы сохраняются Worker в `JobsOperator.Worker/App_Data/packages/`. Каталог исключён из Git.

Веб-приложение передаёт файлы в REST API, API отправляет их в Worker клиентским gRPC-потоком блоками по 64 КБ, а Worker загружает и выполняет сборки в собственном процессе. Загружайте только доверенные DLL. Аутентификация и изоляция пользовательского кода пока не реализованы.

### REST API

HTTP-профиль API по умолчанию доступен по адресу `http://localhost:5244` и предоставляет следующие операции:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/jobs` | Получить все карточки заданий |
| `GET` | `/api/v1/jobs/{jobId}` | Получить одну карточку |
| `POST` | `/api/v1/job-packages` | Загрузить multipart-пакет DLL и запустить найденные `IJob` |
| `POST` | `/api/v1/jobs/{jobId}/start` | Запустить новую попытку |
| `POST` | `/api/v1/jobs/{jobId}/stop` | Остановить текущую попытку |
| `DELETE` | `/api/v1/jobs/{jobId}` | Остановить задание и удалить карточку |

API не выполняет задания и не хранит их оперативное состояние. Его перезапуск не прерывает работающий Worker и после восстановления соединения API снова получает актуальные карточки по gRPC.

## Создание задания

Создайте проект библиотеки классов для `net10.0` и добавьте ссылку на `Jobs`:

```xml
<ItemGroup>
  <ProjectReference Include="../Jobs/Jobs.csproj" />
</ItemGroup>
```

Минимальная реализация задания:

```csharp
using Jobs.Connectors;
using Jobs.JobsEntities;
using Jobs.JobsEntities.Interfaces;

public sealed record InputMessage(string Value);

public sealed class FileJob : IJob
{
    public void Configure(IJobBuilder builder)
    {
        var state = builder.RegisterState<InputMessage>("received-messages");

        builder.ConfigureCheckpoints(new CheckpointOptions
            {
                Enabled = true,
                DelayMillisecond = 5_000,
                PathToCheckpoint = "checkpoints/file-job.json"
            })
            .Source(
                "InputFile",
                _ => new JsonFileConnectorSource<InputMessage>("input.jsonl"))
            .Process(
                "Remember",
                (message, context, cancellationToken) =>
                {
                    state.Push(message);
                    return ValueTask.CompletedTask;
                })
            .Discard();
    }
}
```

Правила построения задания:

- имена источников и состояний должны быть уникальными
- каждый источник должен иметь один обработчик
- каждый конвейер должен завершаться `ConnectToSink(...)` или `Discard()`
- фабрики коннекторов получают `IServiceProvider`, переданный в `JobsOrchestrator`
- обработчик должен учитывать переданный `CancellationToken`
- позиция источника должна указывать на следующий ещё не обработанный элемент
- sink должен вернуть `true` только после успешной записи результата

Для внешнего источника реализуйте `IConnectorSource<T>`, для принимающего узла — `IConnectorSink<T>`. Сериализатор Kafka реализует `ISerializer<T>`; для JSON доступен `CustomJsonSerializer<T>`.

## Состояние и контрольные точки

Состояние регистрируется через `RegisterState<T>(name)`. Текущая реализация хранит элементы как неупорядоченную потокобезопасную коллекцию и предоставляет операции:

- `Push` для добавления элемента
- `GetByPredicate` для получения снимка подходящих элементов

Контрольные точки включаются через `ConfigureCheckpoints`. Во время сохранения оркестратор приостанавливает приём новых элементов, ожидает завершения уже принятых элементов, затем сохраняет позиции источников и снимки состояний в один JSON-файл. Запись выполняется через временный файл с последующей заменой целевого файла.

| Режим | Поведение |
|---|---|
| `ResumeOrCreate` | Восстановить существующий файл или начать с пустого состояния |
| `ResumeOnly` | Требовать существующий файл, иначе завершить запуск ошибкой |
| `CreateNew` | Требовать отсутствие файла, иначе завершить запуск ошибкой |

Если `PathToCheckpoint` не указан, файл создаётся в каталоге `checkpoints` рядом с выполняемой сборкой и получает имя на основе нового идентификатора запуска. Для восстановления между отдельными запусками укажите стабильный путь явно.

Файл checkpoint является источником истины для позиции Kafka. Kafka consumer работает с отключёнными `EnableAutoCommit` и `EnableAutoOffsetStore`, поэтому отдельно зафиксированные consumer offsets не используются.

## Kafka relay

`KafkaRelayJob` читает UTF-8 строки из входной темы, вычисляет длину каждой строки и записывает целое число в выходную тему.

Переменные окружения:

| Переменная | Значение по умолчанию локально | Назначение |
|---|---|---|
| `JOB_MODE` | `sample` | Значение `kafka-relay` выбирает Kafka-задание |
| `KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092,localhost:9093,localhost:9094` | Адреса Kafka-брокеров |
| `KAFKA_INPUT_TOPIC` | `jobs-input` | Входная тема |
| `KAFKA_OUTPUT_TOPIC` | `jobs-output` | Выходная тема |
| `KAFKA_CHECKPOINT_PATH` | `checkpoints/kafka-relay.json` рядом с приложением | Путь к checkpoint |

Запустить весь стенд:

```shell
docker compose up -d --build
```

После запуска доступны:

| Сервис | Адрес |
|---|---|
| Kafka broker 1 | `localhost:9092` |
| Kafka broker 2 | `localhost:9093` |
| Kafka broker 3 | `localhost:9094` |
| Kafka UI | `http://localhost:8080` |

Отправить строки во входную тему:

```shell
docker compose exec kafka-1 /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 --topic jobs-input
```

Прочитать результаты:

```shell
docker compose exec kafka-1 /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 --topic jobs-output --from-beginning
```

Запустить встроенный генератор нагрузки:

```shell
docker compose --profile load run --rm kafka-load
```

Остановить стенд с сохранением томов:

```shell
docker compose down
```

Удаление томов через `docker compose down -v` также удалит данные Kafka и сохранённые checkpoints.

## Диагностика

`JobsOrchestrator.GetJobSnapshot(jobId)` возвращает:

- состояние выполнения: `Running`, `Cancelling`, `Completed`, `Cancelled` или `Failed`
- количество успешно обработанных и записанных сообщений
- время и диагностическое представление последнего входного сообщения
- снимки зарегистрированных состояний
- сообщение об ошибке выполнения

Диагностическое представление одного значения ограничено 4000 символами. Веб-панель обновляет показатели один раз в секунду.

## Текущие ограничения

- автоматические тесты отсутствуют
- публичный NuGet-пакет не выпускается
- гарантии доставки формально не определены и не покрыты тестами восстановления
- один конвейер обрабатывает записи последовательно одним consumer worker
- Kafka-коннекторы по умолчанию работают только с partition `0`
- цепочки из нескольких последовательных процессоров и ветвление графа не поддерживаются
- `JsonFileConnectorSource` наблюдает файл постоянно и не освобождает reader до остановки задания
- `JsonFileConnectorSource.CommitAsync` не реализован
- состояния хранятся в памяти и полностью сериализуются при каждом checkpoint
- нет политики повторов, dead-letter queue, тайм-аутов обработчика и circuit breaker
- нет структурированного журналирования, метрик и распределённой трассировки
- веб-панель не имеет аутентификации, авторизации и изоляции загруженных сборок
- карточки заданий не восстанавливаются после перезапуска Worker, хотя опубликованные пакеты DLL остаются на диске

## Проверка изменений

Основная команда проверки:

```shell
dotnet build JobsOperator.sln
```

Для изменений конвейера или checkpoint дополнительно проверьте обработку входных данных, остановку, повторный запуск и восстановление из ранее созданного файла.
